GenericAgent Agent System Design Overview

Comprehensive compilation based on all docs/ documents | 2026-05-09

Overview

GenericAgent (GA) is a general-purpose, self-evolving LLM agent system designed for task automation within local computing environments. Its core design philosophy is to improve agent performance by optimizing contextual information density, rather than simply extending context length.

Core Positioning

  • Model-Agnostic: The underlying inference engine (Claude, GPT, Gemini, etc.) is swappable without affecting execution logic, tool interfaces, or memory architecture
  • Unified Agent Loop: Each step combines global memory with current task specifications to form an execution context
  • Two Execution Modes: Interactive mode (user-initiated) and Reflective mode (environment-triggered)
  • Minimal Codebase: Core codebase ~3K lines, core agent loop just ~100 lines

Core Design Principles

PrincipleDescription
Tool MinimalismKeep tools to the minimum necessary set to avoid context bloat; satisfy atomicity and combinatorial generalization
Layered MemoryOnly keep a small persistent visible layer (L1); deeper memory (L2~L4) accessed on demand
Self-EvolutionAchieve cross-task experience integration by recording and updating the information environment, without modifying the base model
Context CompressionSet a tight budget of <30K tokens, managed using character-domain heuristic methods

def agent_runner_loop(client, system_prompt, user_input, handler, tools_schema, max_turns=40, verbose=True, initial_user_content=None):

    and tool execution results update system state via structured signals.

    GA supports two execution modes:
    1. Interactive mode: handles user-initiated tasks such as code execution, information retrieval, file operations
    2. Reflective mode: continuously monitors environment changes without user instructions, automatically triggers corresponding tasks when specific conditions are detected

    """

Execution Modes

Interactive Mode

The user initiates a task through CLI or frontend interface, and the agent executes step by step: User Input → put_task(query) → Build prompt, call LLM → LLM returns response (with tool calls) → Execute tools → Update context → Loop until completion.

while turn < handler.max_turns:
    turn += 1

    response = yield from response_gen
    if not response.tool_calls:
        tool_calls = [{"tool_name": "no_tool", "args": {}}]
    else:

                       "args": json.loads(tc.function.arguments)}
                      for tc in response.tool_calls]
    for tc in tool_calls:

        if outcome.should_exit: break
        if outcome.next_prompt:

    # New messages update context, history maintained by Session

Call Flow

User Input ↓ LLM receives tools=TOOLS_SCHEMA ↓ LLM decides which tool to call → returns function_call ↓ agent_runner_loop() parses → maps to same-name Python function ↓ Execution result sent back to LLM → continues reasoning or outputs reply

Creating New Tools

✅ Possible: Script-Level Tools

Created at runtime via file_write + code_run. Example: Image hosting service, OCR debugging script.

❌ Not Possible: Dynamic FC Tool Registration

The tools=[] list is fixed at conversation start and cannot be appended mid-way. Requires editing assets/tools_schema.json + writing Python implementation, effective next session.

Strategy

  • Reusable capabilities → Write as .py module under memory/
  • One-time tasks → Use inline code via code_run directly
  • Persistent services (e.g., image hosting) → file_write to create → code_run to start background process

Design Principles

Code Example: Safety Interception Mechanism

The code_run function in ga.py has a built-in blacklist for dangerous operations, intercepting destructive commands via regex matching:

DANGEROUS_PATTERNS = [
    (r'\brm\s+(-[rR]+|-[rR][fF]|-[fF][rR])\s*/[/\s]', 'Recursively delete root directory'),
    (r'\brd\s+/[sS]\s+/[qQ]\s+[A-Za-z]:\\', 'Recursively delete drive'),
    (r'\bformat\s+[A-Za-z]:', 'Format disk'),
    (r'\bshutdown\s+[/-][sprh]', 'Shutdown/reboot operation'),
    (r':\(\)\s*\{\s*:\s*\|\s*:&\s*\}\s*;?\s*:', 'Fork bomb'),
    (r'\bchmod\s+-R\s+0{2,3}\s+', 'Recursively clear permissions'),
    (r'\breg\s+delete\s+HK', 'Delete registry keys'),
    (r'\btaskkill\s+/[fF]\s+/[iI][Mm]\s+', 'Force terminate process'),
]
# Scan before code execution, intercept on hit
for pattern, desc in DANGEROUS_PATTERNS:
    if re.search(pattern, _code_lower):
        return {"status": "blocked", "reason": f"Dangerous command intercepted: {desc}"}
  • Description Is Behavior Constraint: The tool's description directly influences LLM usage decisions
  • Parameter-Driven: All interactions pass through parameters
  • One Tool at a Time: Each round LLM outputs either one tool call or a plain response
  • Failure Backtracking: Error info sent back to LLM, which autonomously retries or switches approaches

Code Example: Context Compression (Four-Stage Trimming)

The smart_format function in ga.py implements character-domain heuristic compression — this is the concrete implementation of the "Context Compression" design principle:

def smart_format(data, max_str_len=100, omit_str=" ... "):
    """Context truncation and compression: uses head-tail strategy to truncate content, limits single message length.
    GA uses character-domain heuristic methods to manage context budget, controlling length via a four-stage trimming mechanism:
    1. Tool Output Truncation: when a single tool output exceeds threshold, keep head and tail, replace middle section
    2. Tag-Level Compression: replace duplicate working memory blocks with placeholders every 5 rounds
    3. Message Cleanup: recompress when over budget, delete old messages by FIFO
    4. Working Memory Anchoring: append latest conversation summary, round number, and key info to each new message
    """
    if not isinstance(data, str): data = str(data)
    if len(data) < max_str_len + len(omit_str)*2: return data
    return f"{data[:max_str_len//2]}{omit_str}{data[-max_str_len//2:]}"

Code Example: Tool Dispatch Mechanism

The BaseHandler.dispatch method in ga.py maps the tool call name returned by LLM to the same-name Python method:

def dispatch(self, tool_name, args, response, index=0):
    method_name = f"do_{tool_name}"
    if hasattr(self, method_name):
        return (yield from getattr(self, method_name)(args, response))
    elif tool_name == "bad_json":
        return StepOutcome(None, next_prompt=args.get("msg", "bad_json"))
    else:
        return StepOutcome(None, next_prompt=f"Unknown tool {tool_name}")

Code Example: Failure Escalation Chain — 3-Strike Rule

The following code (excerpted from the file_read function in ga.py) demonstrates the "1st failure → intelligent retry" pattern: automatically scans for similar filenames when the file is not found:

except FileNotFoundError:
    msg = f"Error: File not found: {path}"
    tgt = os.path.basename(path)
    # Auto-scan directory for similar files
    cands = list(itertools.islice(
        (c for base in roots for c in _scan_files(base)), 2000))

Code Example: Enforced Summary Mechanism

The summary extraction logic in the turn_end_callback function in ga.py ensures that a <summary> tag is generated every turn:

def turn_end_callback(self, response, tool_calls, tool_results, turn, next_prompt, exit_reason):
    _c = re.sub(r"```.*?```|<thinking>.*?</thinking>", "", response.content, flags=re.DOTALL)
    rsumm = re.search(r"<summary>(.*?)</summary>", _c, re.DOTALL)
    if rsumm:
        summary = rsumm.group(1).strip()
    else:
        # Auto-generate if no summary output
        tc = tool_calls[0]
        summary = f"Calling tool {tc['tool_name']}, args: {tc['args']}"
        if tc["tool_name"] == "no_tool":
            summary = "Directly answered user's question"
        # Also inject a prompt asking for a summary
        next_prompt += "\n\n\nUSER: <summary>呢？？？！\n\n"
    # Store in history for subsequent context injection
    self.history_info.append(f"[Agent] {summary}")

1st Failure Read error logs, understand the cause — Passive Reflection

2nd Failure Probe environment state, get more context — Active Reflection

3rd Failure Deep analysis then switch approach or ask user — Fundamental Adjustment

Core Constraint: No repeated attempts without new information. Each retry must be based on new information or a different strategy.

Multi-Agent System

GenericAgent supports four multi-agent collaboration modes, with core communication based on filesystem async IO protocol + shared memory.

Master-Subagent Mode

The master agent communicates with subagents via the filesystem:

Startup Method:

python agentmain.py --task my_task --input "Task description" [--bg] [--llm_no N]

Map Parallel Mode

Suitable for batch processing of independent isomorphic subtasks:

  1. Master agent prepares N independent input files
  2. Start a subagent for each file (--bg background)
  3. Wait for all to complete → read each output*.txt → aggregate results

Supervisor-Worker Mode

Supervisor — read-only, judge-only, intervene-only, never does hands-on work │ Read output.txt (observe progress) │ Write _intervene / _keyinfo (course correction) ▼ Worker Agent — actually executes tasks

Supervisor intervention triggers: skipping steps, missing details, all talk no action, assertions without evidence, consecutive failures, etc.

Shared Memory Mechanism

All agents share the same memory system: L1 Insight, L2 Facts, L3 SOP/utils, keychain, filesystem.

Multi-Model Configuration

Use the --llm_no N parameter to assign different LLMs to different subagents:

Self-Evolution

GA does not modify the base model; it evolves by recording and updating the information environment. Core strategy: evolve strategies, not tools, keeping the tool layer fixed and separated from the evolving knowledge layer.

Code Example: Memory Distillation Mechanism

The do_start_long_term_update function in ga.py implements "self-evolution" — distilling task experience into long-term memory:

def do_start_long_term_update(self, args, response):
    prompt = """### [Summary & Extract Experience]
Extract information from the most recent task that is [factually verified and long-term valid]:
- Environmental facts (paths/credentials/configurations) → file_patch to update L2, sync L1
- Complex task experience (key pitfalls/prerequisites) → L3 concise SOP
**Only extract information verified successful through action**
**Forbidden**: temporary variables, specific reasoning processes, unverified info, general common sense
"""
    yield "[Info] Start distilling good memory for long-term storage.\n"
    path = "./memory/memory_management_sop.md"
    if os.path.exists(path):
        result = "Auto-read L0 content:\n" + file_read(path, show_linenos=False)
    else:
        result = "Memory Management SOP not found. Do not update memory."
    return StepOutcome(result, next_prompt=prompt)
